# Harness MCP servers

Each harness has its own default for the MCP servers in its configuration: Codex threads in Buzz load none of them, Claude Code loads its own. One optional plugin may override that default for an agent. With no such plugin enabled, launches, thread configuration and behavior are unchanged, and no launch waits for one.

## Plugin API

A plugin declares `host.agentMcp: true` in its manifest. Installation review tells the owner: "Choose which of your harnesses' MCP servers your agents load, including servers Buzz leaves off, and see and block their MCP tool calls. Can start a configured server to list its tools. Cannot add servers or call their tools." The grant cannot add a server or call one. It does let the plugin see and block an MCP tool call before it runs. Listing a server's tools (`inspectHarnessMcp`) starts that server if it is not running. The review's details add: "Only one plugin controls this at a time: the first one to start. When it stops, another plugin with this access can take over."

- `ctx.agents.controlHarnessMcp({ choose(agent) })` registers the one control. The first plugin to register holds it; the owner does not pick which plugin that is. A second registration throws. The control ends with the plugin's scope, and then any other running plugin with the grant can register. Any plugin with the grant can call `harnessMcp` and `inspectHarnessMcp`, whether or not it holds the control.
- `choose` returns an object of overrides by server name: `false` is off, `true` is on, and a list of tool names is on without those tools. A name left out keeps the harness's default, and `undefined` leaves every name out. Any other value for a name means off; an answer that is not a plain object means no server. The control is asked only while its plugin is running.
- The control may also have `call(call)` and `skipped(call)`; see [Call gate](#call-gate).
- `ctx.agents.harnessMcp(agentKey)` returns what the agent's type reports: `tools` (whether single tools can be left out), `inspect` (whether `inspectHarnessMcp` works), `calls: true` when the harness puts this agent's native MCP calls to `call` before they run (never for a protected agent; without it no call can be held, so a call the choice allows runs and `ran` stops the turn), an optional `note`, and `servers` (`name`, `default`, optional `state` and last-seen `tools`; a tool is `name`, an optional `description` and an optional `ungated: true`, kept only when exactly `true`). It is `undefined` when the type does not report.
- `ctx.agents.inspectHarnessMcp(agentKey, server)` lists one server's tools without a model turn and keeps them as the agent's last-seen tools. It rejects protected agents and names the report lacks.

## What core keeps

- A protected agent loads no native MCP server, and the control is not asked.
- A control that throws means no server for that launch.
- A plugin that declares `host.agentMcp`, is enabled, and is not yet running holds a launch until plugin startup settles. If it is still not running, the launch loads no server.
- After the harness starts a session and before its first prompt, the adapter passes what the harness lists as loaded, with the answer `choice` gave that session, to `agents.harness.mcp.started`. Only the plugin that registered the agent's type can call `choice` or `started`, and only for an agent running here. Core reads the agent and its protection from what runs, not from the caller. It throws when a server or tool that was turned off is listed, and the launch stops. This read-back catches a server after the harness started it; it does not prevent the start. The session cannot use it.
- A protected agent of a type that reports its servers passes no protection check until one of its sessions has called `started` with an empty listing under the same protection key. Its other sessions starting do not revoke that; any of its sessions listing a server does. Without it, the type's `protectionUnavailable` reason applies.

## Call gate

Where a harness can stop a call before it runs, its adapter puts each native MCP call to core (`agents.harness.mcp.call`) and core asks the control. As with `started`, only the plugin that registered the agent's type can call `call` and `ran`, for an agent running here, and core reads the agent and its protection from what runs.

- `call(call)` sees `agent`, `session`, `id`, `server`, `tool` (absent when the adapter cannot tell), `arguments`, `hold` (how long core waits, in milliseconds), `direct` and `conversation?: { channel, root?, message? }`. It returns `{ deny: reason }` to stop the call, or `undefined` to allow it. An error, a rejection, a late answer and any other value deny. Without `call`, a call the choice allows is allowed.
- `direct` is true only when the owner's own signed message started the turn and nothing else steered it. A wake, a watch, a timer, an attested sibling's message and a relay workflow are not. `conversation` is where the trigger came from, when it names one: the thread's root only when the message is already in a thread, and `message`, the id of the event that started the turn, when an event did. Core reads both from the trigger it delivered to that agent: a `turn` the adapter passes that core did not deliver to the agent counts as no turn, so `direct` is false and there is no `conversation`. This check shows only that core delivered that trigger to the agent at some time. It does not show that the trigger started the current turn, and core does not freeze the trigger or its event. The plugin that registered the agent's type is trusted to pass the current turn's trigger unchanged.
- Core denies without asking the control when the agent is protected, when the session has no record (see below), when the session's applied choice turns the server off, lists the tool as left out, leaves any tool out and the tool is unknown, or neither names the server nor loaded it, and when no control is running. A server the choice leaves out keeps the harness's default, so one the session loaded counts as on. Otherwise it asks the control and waits `hold` ms; a timeout or an abort of the turn is a denial ("The owner did not answer in time").
- An allow is kept as that call's `id` for its session. If the session starts again, or the plugin stops, before the answer arrives, the call is denied.
- After a harness shows a call as run, the adapter asks `ran`. A call the harness blocked (`rejected`) did not run. An `id` core allowed is used up and did not leak. A call the adapter marks `ungated` (the harness's own setting ran it) is fine where the session's applied choice leaves that server and tool on. Anything else is a call that ran with no allow: core returns true, the adapter stops the turn, and the control's `skipped(call)` is told (without `arguments`, and never for a protected agent).
- A session's record is made by `started`: the choice applied, and the allowed `id`s not yet seen run. Each `started` of the same session replaces its record and empties its allows. A session started with no choice has none. A failed `started` drops it. Core keeps at most 64 sessions per agent and forgets the oldest, so a forgotten session's calls are denied and any that run are reported: the safe side.
- `ungated: true` on a tool means the harness's own setting (for example an "always allow" permission) runs it without asking, so `call` never sees it and only `ran` reports it afterward. An adapter sets it only when it can read that setting; Codex sets none.
- Calls and `ran` are checked only for sessions started with a choice; with no control plugin nothing is put to core.

A gated call is asked, held, and then allowed, denied or timed out, once. After the hold core checks that the session record and the control are still the ones it asked under, so a late allow cannot apply to a newer choice. An allowed call that the harness shows as run is used up; one that runs with no allow is reported as skipped; an allow never seen run is dropped with its session record.

## Adapters

A type declares `harnessMcp: { report(agent), inspect?(agent, server) }`. `report` names servers from the harness's own configuration without starting any. An adapter asks `agents.harness.mcp.choice(agent)` when it launches a session and applies the answer; execution targets report and apply nothing.

### Codex

- Names come from `config/read`. A server chosen on has no thread entry, so `config.toml` applies; with a tool list it gets `disabled_tools` (joined with its own). Every other server keeps `enabled: false`. Buzz never sends `enabled: true` and never sends a name `config/read` does not list.
- A server with `enabled: false` is not started by Codex (checked against 0.164.0 and 0.167.2).
- The read-back calls `mcpServerStatus/list` once for each `config/read` name, with the thread's `threadId` and that `serverName`, which reads the thread's own connection. Without a `serverName`, or without a `threadId`, that call starts servers again, so Buzz never makes it that way. A name the choice leaves out is checked as off. With no choice Buzz makes no status call.
- Compaction resumes its thread with every server off, and reads that back when a choice is in play.
- Tools and state in the report are from the agent's last session's status, so tools appear after its first session with the server on. `inspect` runs an ephemeral thread with every other server `enabled: false` and `thread_unload_delay_secs: 0`, reads status for that `threadId`, then unsubscribes, so Codex unloads the thread and stops its server. No turn runs and nothing is saved.
- `state` is `disabled` only when `config/read` shows `enabled = false`; a server Buzz turned off in a thread has no state.
- The chat-title thread turns every listed server off by name.
- The report says `calls: true` while Codex hooks are on (`features.hooks`) and Buzz's hook bridge serves the agent's threads.
- Gate: with a choice in play, Buzz's hook bridge sends each native MCP `PreToolUse` (hook name `mcp__<server>__<tool>`, the sanitized names) to core, held at most 10 s, and blocks the call with the reason. Plugin hooks for that call get what is left of their 25 s budget, so the two together stay inside Codex's 30 s hook limit. Tool names are matched from the calling thread's own status. The hook gives only Codex's model-visible names, so Buzz matches them to the thread's server names (and its last-seen tools); a name that matches no single server is denied without asking. Buzz's own bridge server and tools are never put to core. With no choice in play, the bridge runs only the plugins' hooks, as before.
- Codex runs the call if the hook errors or runs past its limit. So `ran` is the backstop: a started `mcpToolCall` item (Codex starts none for a call a hook blocked) that nothing allowed stops the turn with `turn/interrupt`, and the control is told. One call can leak. With `features.hooks = false`, or on a thread no bridge serves, there is no gate and only `ran` applies. A subagent inherits its parent thread's servers and hooks. Once its spawn item names its thread, Buzz gates its native MCP calls under the parent's record and passes its items to `ran` when Codex sends them on this connection, so a call nothing allowed stops the parent's turn. Plugin hooks still serve only the parent thread. A native MCP call from any other thread, including a subagent whose spawn has not completed, has no record and is denied; other hooks from such a thread are refused as before.
